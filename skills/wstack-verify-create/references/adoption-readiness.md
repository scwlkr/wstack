# Adoption readiness checklist

Each additional project needs its own adoption pass. The proven pilots are a real CLI fixture validator in wstack, four release-bound HTTP observations in PatriSearch, and four approved BSB Reader/local Exact observations in PatriBible Chrome. Their coverage does not transfer to other features, editions, devices or public releases.

- Read current repository ownership, tracker, delivery and local CI rules. Record unrelated work, current clean candidate and resolved comparison base; isolate owned state under the repository's worktree rules.
- Discover existing help, routes, customized tooling, lifecycle harnesses and verification recipes. Reuse those controls; command definitions own help/capabilities, and one canonical feature map owns feature discovery.
- Source-read the selected implemented behavior. Declare actual user entrypoints, independent expectations, required case/entrypoint pairs, read-only prerequisites, activation gates and uncovered paths before driving.
- Scoped doctor must report each relevant prerequisite and an exact remediation. App readiness remains unknown until actual behavior is exercised. Missing private approved inputs are a block, never an invitation to fabricate, sign, publish or mutate them.
- Build the exact candidate and drive the real surface through `./project`. Retain commands, observations, executable and instance identities, source summary, logs and honest partial coverage. A successful prerequisite check or receipt cannot replace assertions.
- Browser proof retains candidate asset digest, installed executable hash/version, distinct owned preview/browser PIDs, loopback endpoint and private profile identity. Preserve the owning harness's URL/approved-input rules; distinguish local routing from public behavior.
- Inspect DOM/screenshots, raw responses and independent expected text after teardown. Independently check PID absence, port closure, profile/state removal and artifact readability. Qualify actual cancellation and failure reporting, including artifact retention failures. Browser libraries must not race the harness's owned signal cleanup.
- Prove customized command preservation, applicable local gates, independent review and a fresh discovery-to-proof exercise on the final clean candidate. Re-run affected checks after changes and after landing.
- Feature changes maintain affected CLI controls, canonical map entries and recipes together. Recipe owners repair their directory; control gaps outside it and actual product regressions follow bounded owner tasks with unchanged acceptance.
- A complete manual source audit, live drive and cleanup qualify upkeep. Inspect an actual supported runner execution before making runtime claims; record host/resource availability and coverage/rotation limits. Clean recurring runs retain logs quietly; meaningful corrections, failures or required actions notify.

Finish with exact candidate/base, check and live-proof receipts, coverage, evidence paths and remaining actions. Unadopted projects and blocked, dirty, skipped or interrupted paths remain explicitly unqualified.
